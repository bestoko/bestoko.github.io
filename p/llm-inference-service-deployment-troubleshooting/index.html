**使用原则　**文中的镜像标签、设备资源名和模型路径均为模板。生产使用前必须替换为企业已验证版本，并核对驱动、CUDA/CANN、PyTorch/torch-npu 与框架兼容矩阵。

一、基本概念

1. 模型的主要类型

模型类型 输入 → 输出 典型用途 部署关注点
文本生成 文本 → 文本 问答、代码、摘要、Agent 上下文、KV Cache、工具调用
视觉多模态 图片/视频+文本 → 文本 OCR、图表、图片问答 Processor、图片 Token、显存
TTS 文本 → 语音 播报、数字人 首包延迟、RTF、音色
ASR 语音 → 文本 转写、会议、客服 CER/WER、流式、采样率
Embedding/Reranker 文本 → 向量/分数 检索与 RAG 批量吞吐、向量维度

2. 模型文件分别做什么

文件 作用 常见问题
config.json 模型架构、层数、维度、最大位置长度、数据类型 架构不受支持或参数与权重不匹配
*.safetensors / *.bin 模型权重；大模型通常拆成多个分片 缺失、损坏、权限或磁盘不足
*.index.json 权重名称到分片文件的索引 索引引用的分片不存在
tokenizer.* 文本与 Token 相互转换 Tokenizer 与权重版本不一致
generation_config.json 温度、采样、最大输出等默认生成参数 默认值不符合业务预期
processor_config 等 图片、音频等多模态预处理 分辨率、采样率或处理器缺失
**部署前检查　**至少确认：目录完整、SHA256 正确、容器用户可读、模型架构被框架支持、量化格式兼容、是否需要 trust_remote_code。

3. 模型与服务性能指标

类别 指标 含义
文本质量 准确率、事实性、指令遵循、工具调用正确率 回答是否正确、可控、符合业务
TTS/ASR MOS/音色相似度；CER/WER；RTF 语音质量、识别错误与实时能力
交互延迟 TTFT、TPOT/ITL、P95/P99 首字等待、生成速度与尾延迟
吞吐容量 req/s、输入/输出 Tokens/s、并发 单实例可承载的稳定负载
资源 GPU/NPU 利用率、显存/HBM、功耗 硬件是否饱和及是否接近 OOM

4. 推理引擎及选型

推理引擎负责加载权重、处理请求、动态组成 Batch、管理 KV Cache、执行多卡并行并暴露 API。相同模型和硬件下，调度与缓存管理会显著影响吞吐和延迟。

图 3　NVIDIA 与昇腾推理软件栈
框架 适用平台与优势 主要注意事项 建议
vLLM NVIDIA 等平台；生态成熟、OpenAI API、持续批处理 模型和量化支持随版本变化 NVIDIA 通用服务优先
vLLM Ascend 昇腾；沿用 vLLM 接口与调度理念 Driver/Firmware/CANN/torch-npu 强版本约束 昇腾环境优先
SGLang 高效前缀复用、结构化生成、多模态 需按目标模型和业务负载实测 特殊场景对比评估

5. vLLM 原理：整体架构

图 4　vLLM 推理引擎内部组件与数据路径

API Server 接收请求并完成输入处理；Scheduler 在 Waiting 与 Running 请求间分配计算预算；Worker/Executor 在设备上执行模型，并由 Cache Engine 管理 KV Block。多卡场景通过 TP/PP 和 NCCL/HCCL 协同。

6. vLLM 原理：Continuous Batching

图 5　连续批处理的动态请求调度

传统静态 Batch 必须等待最慢请求结束。连续批处理在每个调度步允许新请求加入、完成请求退出，因此设备更少空闲。max-num-seqs 与 max-num-batched-tokens 决定调度边界，过大可能增加 KV Cache 压力与尾延迟。

7. vLLM 原理：PagedAttention

图 6　PagedAttention 的逻辑块、块表与物理 KV Cache

每个请求看到连续的逻辑 KV Block，实际物理块可以分散在显存中。Block Table 负责映射；请求结束后物理块可立即回收，公共前缀还可共享块。这样减少连续大内存分配与碎片浪费，提高可承载并发。
**参数关系　**max-model-len、并发请求数、max-num-seqs、max-num-batched-tokens、缓存精度和内存利用率共同决定容量。调参必须同时观察 TTFT、TPOT、吞吐、队列和 OOM。

3. 多卡与关键参数

参数 用途 操作建议
–tensor-parallel-size 张量并行卡数 与容器可见设备一致；先看拓扑
–max-model-len 最大上下文 按业务上限设置，避免无意义预留
–gpu-memory-utilization 可用于引擎的显存比例 留出运行与波动余量
–max-num-seqs 并发序列上限 结合真实并发逐步压测
–enable-prefix-caching 共享前缀缓存 公共系统 Prompt 多时验证收益

apiVersion: apps/v1
kind: Deployment
metadata:
  name: vllm-qwen
  namespace: llm-serving
spec:
  replicas: 1
  strategy:
    type: Recreate
  selector:
    matchLabels:
      app: vllm-qwen
  template:
    metadata:
      labels:
        app: vllm-qwen
    spec:
      terminationGracePeriodSeconds: 120
      containers:
        - name: server
          image: registry.example.com/ai/vllm:<已验证版本>
          args:
            - --model=/models/qwen
            - --served-model-name=qwen-instruct
            - --tensor-parallel-size=2
            - --max-model-len=8192
          ports:
            - name: http
              containerPort: 8000
          resources:
            limits:
              nvidia.com/gpu: "2"
            requests:
              cpu: "8"
              memory: 32Gi
          volumeMounts:
            - name: model
              mountPath: /models
              readOnly: true
            - name: shm
              mountPath: /dev/shm
          startupProbe:
            httpGet:
              path: /health
              port: http
            periodSeconds: 10
            failureThreshold: 90
          readinessProbe:
            httpGet:
              path: /health
              port: http
      volumes:
        - name: model
          persistentVolumeClaim:
            claimName: llm-models
        - name: shm
          emptyDir:
            medium: Memory
            sizeLimit: 16Gi

5. 生产部署五个重点

1.　Pod 多卡资源必须在同一节点同时满足，注意资源碎片。

2.　startupProbe 覆盖最坏模型加载时间，readiness 通过后才接流量。

3.　大模型发布可能需要双份设备容量；不足时采用 Recreate 或蓝绿集群。

4.　网关设置鉴权、最大输入/输出 Token、并发、队列和流式超时。

5.　上线前完成预热、压测、优雅退出和回滚演练。

四、问题排障

图 9　模型服务分层排障路径

1. 标准排障顺序

坚持自底向上：硬件 → 驱动/固件 → CUDA/CANN → 容器设备 → PyTorch/torch-npu → 推理引擎 → 模型文件 → Kubernetes → Service/Gateway → 请求与容量。每一步保存时间戳、命令输出和最近变更。

2. 典型问题速查

现象 优先检查 常见处理
容器看不到 GPU/NPU 宿主机状态、运行时、设备映射 修复 Device Plugin/Runtime 或设备权限
模型启动失败 首个 ERROR、模型文件、版本矩阵 校验权重，固定兼容镜像
CUDA/NPU OOM 发生阶段、上下文、并发、其他进程 缩短上下文、降并发、量化或增加并行
NCCL/HCCL 挂起 Rank、拓扑、网络、共享内存 先跑通信测试，再启动模型
Pod Pending Events、扩展资源、PVC、亲和性 释放/增加设备或修正调度约束
探针反复重启 启动耗时与 probe 配置 增加 startupProbe 窗口
Service 不通 Pod Ready、selector、Endpoint、端口 逐层验证 Pod IP 与 Service
TTFT 突然升高 队列、长输入、Prefill、网关 限制输入和并发，检查扩容与过载

五、总结

需要记住的六件事

1.　先判断模型类型，再检查 config、权重、Tokenizer/Processor 和量化格式。

2.　TTFT 主要受排队与 Prefill 影响，TPOT 主要反映 Decode；容量必须看尾延迟和错误率。

3.　vLLM 的核心是 Continuous Batching 与 PagedAttention/KV Cache 管理。

4.　NVIDIA 通用部署优先 vLLM；昇腾优先 vLLM Ascend；特殊场景再评估 SGLang。

5.　Docker 负责快速验证，Kubernetes 负责资源调度、服务治理和生产发布。

6.　故障排查从硬件到底层逐层向上，不要一开始就反复改模型参数。

上线前最小检查清单

  • 模型文件完整、版本可追溯，目标框架支持

  • 硬件、驱动、计算栈、PyTorch 与框架版本矩阵已验证

  • API、流式输出、长输入、异常请求和取消行为通过

  • 目标并发下 TTFT、TPOT、吞吐、显存/HBM 和错误率达标

  • Kubernetes 探针、优雅退出、流量限制和回滚经过演练

  • 设备、框架、请求和 Kubernetes 指标已接入监控告警
**最终原则　**生产结论以目标模型、目标硬件和真实业务负载的压测为准。不要把社区单点性能数据直接当作本系统容量。
